Practical guide / Published 26 November 2026

The agent crossed into another company. What evidence should travel with it?

An agent can authenticate successfully and still lack authority for the requested action. At an organizational boundary, the receiving service needs enough evidence to identify the principal, recognize the agent, constrain the mandate and explain the decision.

Principal Agent Resource Mandate Decision

01 / The boundary

Identity answers who. Authorization answers whether.

Cross-company access brings at least three parties into one decision: the principal on whose behalf the work occurs, the agent performing it and the resource server enforcing its own policy.

Principal

Who is accountable?

Name the human or organization behind the request and the identity authority the receiver is prepared to trust.

Agent

Which software is acting?

Give the agent a distinct identity and bind the request to the credential holder. A borrowed bearer token is weak evidence of the acting software.

Resource server

What will be allowed?

The receiver validates the evidence, applies local policy and decides whether this action on this resource is within scope now.

02 / Seven handoff checks

What should survive the trust boundary?

01

Principal

Identify the human or organization on whose behalf the request is made and the issuer asserting that identity.

02

Agent

Identify the software agent separately from its principal, including the agent identity issuer and credential binding.

03

Target

Bind authorization to the intended resource, audience and requested action so evidence cannot be replayed elsewhere.

04

Mandate

State the allowed purpose, scope ceiling and relevant constraints. Downstream delegation must not expand authority.

05

Possession

Check proof that the requesting agent controls the credential or key expected for this request.

06

Supervision

Record whether the action is autonomous, requires a supervisor or needs fresh human approval at a defined threshold.

07

Lifecycle

Verify expiry and revocation, then retain a correlation identifier and decision evidence for review.

03 / Twenty-minute handoff test

Trace one request from principal to decision.

Use a real design or controlled test. Do not place production credentials, personal data or customer secrets in the worksheet.

  1. Choose one agent request that crosses an organizational or cloud trust boundary.
  2. Record the principal, agent identity, target resource and exact requested action.
  3. Locate evidence for the mandate, credential possession, supervision rule, expiry and revocation check.
  4. Record the receiver's allow, deny or escalate decision and the correlation identifier for its evidence.
  5. Mark missing or ambiguous evidence as a gap. Do not treat a successful login as proof of authority.

04 / Concrete example

An enterprise agent requests a cloud action.

A useful handoff separates evidence from the final enforcement decision.

Presented evidence

Identity and mandate

The request carries principal and agent identity claims, an intended audience, a narrow action scope and short-lived validity.

Receiver checks

Trust and context

The receiver validates issuer, signature, audience, expiry, resource binding and any local supervisor requirement.

Recorded result

Allow, deny or escalate

The receiver applies its own policy and keeps a reviewable decision reference. Evidence does not bypass resource policy.

05 / Naming boundary

A name can help discover trust metadata. It cannot grant authority.

An ENS name could help software locate an agent profile, issuer, policy or service reference. It cannot prove possession, establish the principal, widen a mandate, satisfy an approval rule, perform revocation checks or force a resource server to allow an action.
